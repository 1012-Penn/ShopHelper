## 2. 第一波：四章并行，完成后统一集成

### CH15：答案可证实与引用约束

**问题。** 前置证据闸只判断材料是否足够，最终生成器仍可混淆商品、漏适用条件、把多个引用挂在同一句上。当前线上 token 在最终检查前已经发送，事后发现错误也无法收回。

**范围。** 把最终答复改为“事实声明—证据 ID—适用条件”的结构化中间表示；只允许引用当前回合的原文证据，逐条核对支持关系和政策版本；缺证据时澄清、有限帮助或拒答。设计经校验再发送的 SSE 协议，记录校验失败和改写原因。保留现有回答器为可回滚对照，不放松前置闸。加入检索文档携带恶意指令的对抗用例，工具权限仍由代码控制。

**验收。** 先用 dev 集调方案，冻结集不调阈值。在线回答路径和评测路径共用答复核心；报告逐题 strict accuracy、claim 级无证据断言、引用支持、条件覆盖、误拒与延迟。冻结集以 CH11 的 11/62、79/150、7/70 为明确对照；预先登记改善门槛，并对每个新增拒答说明原因。恶意检索文本不能导致越权工具调用或无证据断言。

**主要文件所有权。** `app/grounding/` 新模块、`app/graph/agent.py`、回答契约测试。尽量不改 `app/graph/builder.py`、用户路由和 CH11 题集。

### CH16：持久执行、并发与资源预算

**问题。** 进程内 checkpoint 与线程集合不支持跨 worker 的真实续跑；SSE 断开、进程崩溃和节点重放的业务语义尚无统一契约。CH12 的审计表可查询，但不是恢复日志；超时后底层调用可能继续计费。

**范围。** 选一套持久 checkpoint/run-state 方案，定义 `run_id`、会话串行化、节点重入、用户取消与服务崩溃后的恢复入口。业务写入统一用持久幂等键；预算采用请求前原子预留、结束结算，明确不能取消的上游调用如何计费。MySQL 继续保存业务真源；checkpoint 和业务写入之间不假装有跨库事务。对 Milvus Lite 单进程锁保持当前约束，不能用“两个 API worker”冒充向量库多实例。

**架构选择待讨论。** 推荐先做“官方持久 checkpointer（PostgreSQL）+ MySQL 业务库”的可验证原型，代价是双库运维；另一方案是 MySQL 自建 run-state/重放协议，服务更少但需要自行证明 LangGraph 状态语义。不能仅把 InMemorySaver 换成 SQLite 文件就宣称多实例可用。

**验收。** 在真实数据库上至少两 worker、同会话并发、每个关键节点前后杀进程，证明最终会话与工具写入没有重复、串线或丢失；从新进程查询未完成 run 的状态并恢复。单次调用超时、总体预算、费用预留和 SSE 断开均有可审计结果；无法硬取消的调用明确记为软超时。

**主要文件所有权。** `app/runtime/` 新模块、`app/graph/builder.py`、`app/routers/chat.py`、checkpoint 配置与故障注入测试。与 CH17 的 `chat.py` 改动在集成分支统一合并。

### CH17：终端用户身份、资源隔离与工具授权

**问题。** CH14 只保护管理后台。当前 `/api/conversations/{id}/messages`、`/api/sessions/{id}/history` 等端点仅检查 ID 存在；`/api/chat` 可传任意已有会话 ID；工单确认也只查会话是否存在。个人原型可以使用模拟数据，但不能把这种状态称作具备多用户隔离。

**范围。** 第一阶段推荐签名访客身份 Cookie，绑定会话、消息、反馈、工单和确认预览；管理员身份与终端用户身份分开。所有用户 API 使用同一资源授权依赖，服务端决定 owner，不信任模型、MCP 描述或客户端传来的 ID。写工具确认绑定身份、会话、工具与参数；再加入知识块/MCP 返回内容中的提示注入测试。注册登录或第三方 SSO 留待真实业务需求，不为了简历加账号体系。

**验收。** 两个访客的 IDOR 矩阵：读历史、续聊、提交/重试工单、反馈、确认预览和 SSE 回连全部交叉验证；越权一律拒绝且无业务副作用。同访客刷新和服务重启后仍能续聊；管理员只能在明确授权时访问管理 API。记录安全测试与审计行，不把“前端隐藏按钮”当权限控制。

**主要文件所有权。** `app/identity/` 新模块、`app/routers/conversations.py`、`sessions.py`、`tickets.py`、`feedback.py` 及 API 安全测试。`chat.py` 只加必要的 owner 校验，最终与 CH16 集成。

### CH18：线上同口径评测与系统验收

**问题。** CH11 评测回答器与线上 system prompt/工具链不同；现有冻结集可比较检索方案，却不能直接证明用户在真实图上得到正确答复。模拟数据和 CH10 合成分类集也不能推出真实业务泛化。

**范围。** 新建“线上图回放”评测入口，固定模型、prompt、路由、工具 fixture、索引版本、预算与种子；同题记录检索、证据闸、最终答复、引用、工具调用、延迟与费用，按 L1–L5 分层报告。保留 CH11 frozen-v1 和 regression-v1 原文件及历史数字。增加人工抽审样本与不可信文档、跨用户访问、故障注入桶；所有新题先进入 dev，冻结后才作一次正式对照。Langfuse trace 与本地报告用 `run_id` 对齐。

**验收。** 同一 contract 缓存重放指标逐位一致；线上图与评测入口对同一输入生成相同的路由/答复契约。CH12 baseline、decompose_once、controlled_loop 三组在统一付费预算下真实对照，逐题报告多跳、政策冲突、无证据断言和误拒的得失，并同时报 P50/P95、调用数与成本。CH10 F1 始终注明“模拟留出集 n=163”，若没有脱敏真实问题，不宣称真实分布效果。

**主要文件所有权。** `scripts/eval_online_*`、`tests/eval/online_*`、`docs/eval/ch18-*` 和数据/报告工具；只通过公开接口消费 CH15–CH17 模块，不直接编辑它们的实现文件。首阶段先搭骨架和 baseline，最终质量验收在四章合并后进行。

## 3. 并行与集成规则

1. 四个 worktree 都从已确认的 `origin/main` 起步，分支前缀分别为 `codex/ch15-*` 至 `codex/ch18-*`；CH12、CH13 分支保持原样。每章单独 spec、plan、dev-notes、测试和最小复现命令。
2. CH15 不改会话路由；CH16 不改答案 prompt；CH17 不改 graph/checkpointer；CH18 不改业务实现。`app/routers/chat.py`、`app/models.py`、`db/init.sql`、README 等共享文件允许小改，但必须在最终集成分支逐项合并并复跑验收。
3. 各章使用私有测试库与索引副本。Milvus Lite 单文件不并发持有；付费模型评测串行执行，先有全局费用预留或独占评测锁，不能把台账写锁当作调用预算锁。
4. 集成顺序：先 CH17 身份边界与 CH16 运行态，再 CH15 答复链路，最后 CH18 跑真实全链路对照。开发可并行，集成和最终付费对照按依赖串行。每次合入后确认旧默认路径仍可回滚。
5. CH13 保持旁路。若未来要合入索引服务，先修“连续更新后回滚的版本身份碰撞”和“图引用被候选上限截断”，再重新做配对评测；不将现有单次更新演练称为生产恢复证明。

## 4. 第二波候选，不与第一波混在一起

- **Milvus Standalone 迁移与故障演练。** Lite 适合原型；要宣称多实例检索与在线备份，先用服务版做同索引、同题一致性、入库可见性和压测。是否需要分布式 Milvus 由负载证据决定。
- **真实业务工具接入。** 当前订单、物流和售后 MCP 返回模拟数据；没有业务系统契约和授权边界时，不增加“真实订单服务”或 Go 微服务。若出现独立业务域、明确 SLA 与接口契约，再评估用 Go 承担该服务；Agent 主流程继续留在 Python。
- **CH10 外部效度。** 主题分类微 F1=0.932 的留出集主要来自模拟题；扩大经同意脱敏的真实问题后再评估漂移、人工复核成本与是否值得维持专用模型。

## 5. 需要用户参与的架构取舍

1. CH16 的持久图状态：接受 PostgreSQL 只存 checkpoint、MySQL 继续存业务数据，还是优先单库 MySQL 并承担自建恢复协议的验证成本？推荐前者，前提是先做双库故障演练。
2. CH17 的用户模型：先用签名访客身份确保隔离，还是本轮同时做注册登录？推荐访客身份，能解决当前可复现的越权问题且不引入无业务需求的账号系统。
