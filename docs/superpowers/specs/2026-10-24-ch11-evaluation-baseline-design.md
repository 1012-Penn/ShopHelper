## 0. 一页结论

1. 现有 47 正 + 13 负、约 59 chunk 的基线适合做回归，但已饱和（历史 `hybrid_rerank` 严格 R@10=1.000），无法证明新架构的增益。ch11 的首要产出不是“更高的分数”，而是**一套后续方案不能各造一套题的共同评测契约**。
2. 评测必须把五件事分开计量：检索命中、证据足够、回答正确、合理拒答/澄清、过程成本。任何单一总分都不能抵消“无证据断言”和“硬负例误放行”。
3. 语料来源已由用户决定：以“结构化业务事实（source of truth）+ 受控渲染/手写知识文档”为主，公开电商文本只作措辞参考、不直接进入语料。理由是可审计、可构造版本冲突与跨文档证据、避免许可/隐私/评测污染；代价是前期建模与审校工时更高、语言真实性较弱。
4. 数据集建议分开发集、冻结测试集、回归集三层；冻结集在 ch12/ch13 开发前锁定，后续只允许新增版本、不允许静默改题。
5. C04/C05 已由用户决定改标：C04 按有条件帮助（`answer_with_conditions`）、C05 按需核验（`verify_then_answer`）处理，不能通过调 prompt 把旧标签硬刷成可答；保留原题及历史标签/成绩，不覆盖旧报告。若业务确实要确定性结论，必须先补知识规则并升语料版本，再重新标注和冻结。
6. 已由用户决定先做 M1 规模（约 6–8 份文档、120–180 chunk、210 道题），是否扩到 M2 依 M1 结果再定。语料来源已按第 3.4 节决定；费用上限与模型选型仍未决。

## 2. 评测要回答的问题与指标契约

### 2.1 五个必须分开回答的问题

| 层 | 问题 | 典型失败 |
|---|---|---|
| L1 检索 | 该题需要的证据，是否进入 Top-K？ | 漏检、实体错配、版本选错 |
| L2 证据 | 给出的证据是否足以支持回答/澄清/拒答？ | 话题相关但不回答问题；多约束缺一条；冲突未识别 |
| L3 回答 | 回答的事实、条件、引用是否正确？ | 答错数值、漏条件、无依据断言、引用不支持 |
| L4 行为 | 该答、该澄清、该核验、该拒答，是否做对？ | 误拒、误答、把“需鉴定”说成“确定结论” |
| L5 过程 | 质量收益花了多少调用、token、延迟和费用？ | 多轮补检索没有净收益；重试/降级被隐藏 |

每层都必须能按 `split × bucket × expected_behavior` 下钻，并保留逐题轨迹；报告不得只给一个总分。

### 2.2 标签体系（与旧字段兼容）

新增 `expected_behavior`，并把旧的 `answerable` 语义收窄为“是否存在合法的域内响应路径”：

| `expected_behavior` | 含义 | 旧 `answerable` | 允许的结论强度 |
|---|---|---|---|
| `answer` | 知识库直接给出确定事实 | true | 确定结论 |
| `answer_with_conditions` | 满足条件才成立，必须说出条件 | true | 有条件结论 |
| `verify_then_answer` | 需要照片/检测/人工核验，不能直接下结论 | true | 流程 + 有限帮助，禁止确定性判定 |
| `clarify` | 缺少槽位（商品、订单、会员、地区、日期等），应先问 | true | 只问必要问题，不编答案 |
| `refuse` | 域外、知识库无依据且无合理路径 | false | 明确拒答/转人工 |

补充标签：

- `evidence_state`：`sufficient` / `partial` / `insufficient` / `conflicting`。它描述证据本身，不等同于 `answerable`。
- `required_slots`：澄清题必须补齐的槽位，如 `sku`、`order_id`、`member_status`、`region`、`purchase_date`、`damage_photo`。
- `required_conditions`：有条件回答必须出现的条件，如“会员身份”“商品参与活动”“签收 7 天内”“商品完好”。
- `forbidden_claims`：禁止出现的断言，如“所有商品 95 折”“开胶一定算质量问题”“保证明天到”。
- `gold_facts`：结构化事实，供确定性判分；`required_evidence` 继续使用逐字 quote + AND 语义，供检索/证据判分。

### 2.3 指标定义、分母与阻断项

#### L1 检索层

分母默认是“该 split 中 `required_evidence` 非空的样本”；澄清/拒答题若无证据组则从检索分母剔除并报告 `n`。

| 指标 | 定义 | 说明 |
|---|---|---|
| `R@K` | 所有 evidence 组都进入 Top-K 的题数 / 分母 | 沿用 `coverage_rank` |
| `group_recall@K` | 命中的 evidence 组数 / 总组数，再对题取平均 | 观察多跳题缺哪一组 |
| `single_chunk@K` | 单个 chunk 同时覆盖全部 evidence 的题数 / 分母 | 区分“能拼装”和“一块就够” |
| `MRR@K` | 首次覆盖全部 evidence 的名次倒数均值 | 排名质量 |
| `evidence_precision@K` | 检索到的支持 chunk 数 / 检索到的 chunk 数 | 需要标注支持 chunk 集 |
| `hard_negative_hit_rate` | 负样本中任何 chunk 进入 Top-K 的比例 | 诊断项，不等于误答 |

报告必须给 `n`、分桶、宏平均与微平均；不得用微平均掩盖小桶。

#### L2 证据层

证据层要回答“是否足以支持下一步行为”，而不是只判“像不像”。

| 指标 | 定义 | 阻断 |
|---|---|---|
| `gate_false_accept_rate` | 金标 `insufficient/conflicting` 却被判为可回答的题数 / 这类题数 | **是** |
| `gate_false_block_rate` | 金标 `sufficient` 且检索命中，却被拦下的题数 / 这类题数 | 否，但需报告 |
| `partial_handling_rate` | 金标 `partial` 的题中，系统给出澄清/核验/条件说明而非确定结论的比例 | 否，纳入 L4 |
| `conflict_detection_rate` | 版本冲突题中，系统识别冲突并采用生效版本的比例 | 是（对冲突桶） |
| `citation_support_rate` | 有引用的结论中，引用 chunk 确实支持该结论的比例 | 是（对答案层） |
| `unsupported_claim_rate` | 无证据支持的结论数 / 结论总数 | **是** |

“检索未命中”与“证据闸误判”必须分开归因：检索没找到证据时，不应把 gate 的失败算成 gate 的错误，除非 gate 仍然放行了空/无关证据。

#### L3 回答层

| 指标 | 定义 | 分母 |
|---|---|---|
| `answer_accuracy_strict` | 全部必需事实 + 必需条件正确，无 `forbidden_claims`，引用可支持 | 所有 `answer`/`answer_with_conditions`/`verify_then_answer` 题 |
| `answer_accuracy_partial` | 必需事实的加权覆盖率 | 同上 |
| `condition_coverage` | 出现的必需条件数 / 必需条件数 | `answer_with_conditions`、`verify_then_answer` |
| `forbidden_claim_rate` | 出现任一禁止断言的题数 / 分母 | 全部回答题；**阻断** |
| `clarify_slot_recall` | 问到的必需槽位数 / 必需槽位数 | `clarify` 题 |
| `clarify_precision` | 相关问题数 / 总追问问题数 | `clarify` 题，防“连环追问”刷分 |

判分顺序：先做确定性检查（数值/单位/条件/禁用断言/引用映射），再用 LLM 裁判处理同义转述；裁判只判“事实与条件是否被支持”，不判语气。裁判 prompt、模型、温度、版本必须进 manifest；人工抽审分层不少于 20%，并报告裁判与人工的一致率。裁判不能作为唯一真值。

#### L4 行为层

| 指标 | 定义 | 阻断 |
|---|---|---|
| `under_refusal_rate` | 金标 `refuse` 却给出实质答案的题数 / 拒答题数 | **是** |
| `over_refusal_rate` | 金标 `answer/answer_with_conditions/verify_then_answer/clarify` 却被拒答的题数 / 这些题数 | 否，但设上限 |
| `correct_refusal_rate` | 金标 `refuse` 且正确拒答/转人工的比例 | 否 |
| `clarify_appropriateness` | `clarify` 题中只问必要槽位、未编造答案的比例 | 否 |
| `conditional_compliance` | 有条件题中，未把条件结论说成无条件结论的比例 | **是** |
| `verification_compliance` | 需核验题中，未直接判定“是/否质量问题”的比例 | **是** |

核心原则：**误放行（无证据断言、硬负例答成事实、把需鉴定说成确定结论）是阻断项；提高回答率不能抵消误放行。**

#### L5 过程层

按题记录并在 `split × bucket` 聚合：

- LLM 调用次数、输入/输出 token、按版本化价格表估算的费用；
- 检索调用次数、工具调用次数、重试次数、降级/超时/异常；
- 端到端墙钟延迟 P50/P95；如在线评测，另记首 token 时间；
- 每题失败分类、停止原因、最终使用的证据 ID。

质量对照必须同时报告“质量 + 调用数 + token + 延迟 + 费用”。离线质量跑与在线延迟跑分开，不能把缓存命中的离线结果当作线上延迟。

## 3. 语料扩展策略

### 3.1 保持电商客服业务闭环

语料围绕一条可闭环的业务链扩展，而不是孤立 FAQ：

1. **商品目录**：12–20 个 SKU，覆盖型号、变体、价格、规格、兼容配件、替代型号、在售/停产状态。
2. **订单**：8–12 个合成订单，覆盖未支付、已支付未发货、已发货、已签收、已取消、退货中、已退款；带时间戳、金额、会员等级、地区。
3. **政策**：退货、换货、保修、运费；按商品类目、订单状态、地区、签收日期限定适用范围。
4. **优惠**：会员折扣、满减/包邮门槛、地区补运、活动互斥与叠加条件、生效日期。
5. **售后异常**：丢件、破损、延迟、大件取件、安装调试的处理时限与责任划分。
6. **知识文档**：FAQ（短答）、政策（规范条款）、手册（流程/表格）、商品目录（参数）、活动说明（条件）、核验指引（需鉴定场景）。

跨文档引用要真实存在：FAQ 指向手册、政策版本互相替代、活动条件引用会员等级和商品排除项、订单状态决定适用哪条政策。

### 3.2 结构化事实与知识文档分离

建议新增（后续实施，不在本阶段创建）：

```text
corpus/facts/*.yaml          # 结构化事实，评测和文档的共同真源
corpus/sources.yaml          # 每条事实/文档的来源、许可、日期、审核人
corpus/manifest.yaml         # 文档注册、content_type、语料版本与规模上下限
knowledge/*.md               # 唯一运行时知识文档源，不再维护 corpus/docs 副本
tests/eval/splits/*.jsonl    # 开发/冻结/回归集
tests/eval/manifests/*.json  # 语料、索引、模型、prompt、阈值版本
```

- 实施决定（2026-10-24）：`knowledge/*.md` 是唯一文档源，**不创建 `corpus/docs/`**。原因是两份文档副本会在迭代中漂移，且评测与建库都只读 `knowledge/`；事实与来源仍放 `corpus/`，二者通过逐字 quote 校验绑定。
- 每个事实有稳定 `fact_id`、实体 ID、键、值、单位、适用条件、生效区间、来源。
- 知识文档由事实渲染或手写，但**文档正文只放业务表述，不放评测题、答案、fact_id 标注或“标准答案”**。文档与事实的映射放在 sidecar/manifest，避免污染检索。
- 评测脚本同时读文档（用于证据 quote）和事实（用于答案判分），模型只读文档。

### 3.3 必须构造的关系、版本与冲突

| 类型 | 例子 | 期望行为 |
|---|---|---|
| 商品关系 | SH-E300 与 SH-E120 的降噪/价格差异；某配件只兼容一个型号 | 问 A 不能用 B 的参数回答 |
| 替代/兼容 | “E300 的替代型号是什么”需要跨商品条目 | 多跳/关系题 |
| 订单状态 | 未发货可取消；已发货只能拒收/退货；已激活虚拟商品不可退 | 先查状态再套政策 |
| 政策适用条件 | 7 天无理由需商品完好；定制类仅质量问题可退；生鲜限签收当日 | 条件必须说全 |
| 版本冲突 | 退货窗口 v1=7 天、v2=15 天，按签收日期适用；旧订单用旧版 | 识别生效版本，不混用 |
| 跨文档证据 | FAQ 只给入口，金额/时限在手册表格；政策与手册不一致时按更友好口径 | 组合多份证据 |
| 地区/重量 | 首重、续重、偏远补运、港澳台/海外件 | 表格检索 + 计算 |
| 优惠互斥 | 会员 95 折是否与活动叠加、包邮门槛是否按合并订单总额 | 条件/互斥判断 |
| 实体错配 | 问不存在的订单/型号；问 A 型号但库内只有 B | 澄清或拒答，不张冠李戴 |

### 3.4 数据来源与可审计性（已决定）

**2026-10-24 用户决定**：以可审计的模拟电商事实与政策为语料主来源；公开文本只作措辞参考，不直接复制进语料。该决定同时约束语料、标注与报告口径。

| 来源 | 定位 | 约束 |
|---|---|---|
| 结构化业务事实 + 受控渲染/手写文档 | **主来源** | 每条事实有 `fact_id`、来源、生效区间；文档由事实渲染或按事实表手写 |
| 公开电商政策/FAQ | **只作措辞参考** | 不直接复制；仅借鉴句式/术语；进入语料前必须改写、记许可并复核事实一致性 |
| LLM 生成 | **只辅助措辞/问法变体** | 不生成金标答案；每条内容过事实校验器 + 人工复核 |

**理由**：能让每条 gold fact 追到证据 quote，精确构造版本冲突、跨文档证据和实体错配；避免公开数据的许可、时效、隐私与评测污染；也便于做答案泄漏扫描。

**代价**：前期要建事实 schema、渲染/一致性校验和审校流程，工时高于直接抓 FAQ；语言真实性弱于真实客服文本，结论不能外推到真实业务分布；若参考公开文本，仍需逐条做许可与改写审查。

审计要求：

- `corpus/sources.yaml` 记录来源类型、URI/文档号、获取日期、许可、作者、审核人、置信度。
- 合成事实的来源写“内部业务规则 + 规则编号”，不是“模型说的”。
- 公开来源必须记录许可并改写；无法确认许可的内容不进入语料。
- 所有 gold fact 必须能映射到至少一条证据 quote；所有 quote 必须在文档中逐字存在。
- 事实库做引用完整性校验：商品/订单/政策 ID 存在、生效日期有序、版本替代关系无环、同一事实不在两处给出不同值（除非明确是版本冲突且带生效区间）。

### 3.5 规模分阶段目标

| 阶段 | 文档 | chunk | 结构化事实 | 标注题量 | 用途 |
|---|---|---|---|---|---|
| P0 现状 | 3 | 约 59 | 无独立事实库 | 60（47+13） | 回归基线 |
| M1（ch11 最低验收） | 6–8 | 120–180 | 150–250 | 210（dev 60 / frozen 90 / regression 60） | 建立契约、跑通分层指标 |
| M2（ch13 对照前） | 10–12 | 250–400 | 300–500 | 300（dev 90 / frozen 150 / regression 60） | 有足够多跳/冲突/负例题做配对 |
| M3（可选） | 15+ | 500+ | 600+ | 500+ | 只有在前两阶段仍饱和时再做 |

M1 已由用户决定先做；M2 是否启动依 M1 结果再定，不是既定计划。

扩规模的触发条件不是“想更大”，而是：冻结集中至少若干桶的 R@10 仍接近饱和、硬负例/实体错配/冲突题不足、或配对比较的置信区间过宽。每阶段都要保留上一阶段的冻结集与报告，不覆盖。

### 3.6 防止答案泄漏

1. `build_kb` 只索引 `knowledge/*.md`；`tests/eval/`、`corpus/facts/`、报告目录不得被索引。
2. 文档中不得出现评测 ID、原题、标准答案、`forbidden_claims` 或“本题应回答……”字样。
3. 加自动检查：评测 query 与知识文档的 n-gram 重合度、答案句与文档句的近似重复；阈值和命中的个案要进报告。
4. 冻结题不得由知识文档反向生成；问法变体只用于开发集，不进入冻结集。
5. `mine_qa` 不得从评测题或其近义改写中挖知识；挖出的内容入语料前要过去重和泄漏扫描。
6. 查询改写缓存、评测报告、人工审核记录不进入 `knowledge/`。
7. 若使用 blind 子集，预测结果与金标分离存放，模型上下文永远不包含金标。

## 4. 数据集设计

### 4.1 三层 split

| split | 用途 | 允许的操作 | 规模（M1） |
|---|---|---|---|
| `dev` | 调检索、改写、prompt、阈值 | 可反复看逐题结果、可改题 | 60 |
| `frozen-v1` | ch12/ch13 同题对照 | 开发前锁定；只跑里程碑；不得按题调参 | 90 |
| `regression-v1` | 旧 60 题回归 | 原样保留，标签修订另记版本 | 60 |

- 旧 `ch04_eval_set.jsonl` 与 `ch09_junk_set.jsonl` 不覆盖，作为 `regression-v1` 的物理来源；C04/C05 的修订写入新标签版本，不抹掉历史成绩。
- `frozen-v1` 在 ch12/ch13 任何方案开发前提交哈希；首次用于对照后，任何改题都产生 `frozen-v2`，并要求所有方法重新基线，不能只重跑新方法。
- 报告必须写明本次使用的 split、哈希、题量和标签版本。

### 4.2 题型

| 桶 | 定义 | M1 冻结集题量 | 判分重点 |
|---|---|---|---|
| `single_hop` | 单文档单事实 | 18 | 事实精确、引用正确 |
| `multi_hop` | 跨文档/跨工具组合 | 16 | 证据组覆盖、组合推理 |
| `multi_constraint` | 多条件同时成立 | 14 | 条件覆盖、禁止漏条件 |
| `entity_mismatch` | 型号/订单/配件错配 | 10 | 不张冠李戴，澄清/拒答 |
| `policy_conflict` | 新旧版本/冲突条款 | 8 | 生效版本识别、冲突说明 |
| `hard_negative` | 同域但知识库缺关键事实 | 10 | 不误答；可拒答或澄清 |
| `clarify` | 缺槽位，应先追问 | 8 | 槽位召回、不过度追问 |
| `ood` | 域外噪声 | 6 | 拒答/转人工 |
| **合计** |  | **90** |  |

M1 冻结集固定为 90 题（18+16+14+10+8+10+8+6=90），与第 3.5 节、4.1 节和 manifest 的 `n=90` 一致；不再保留“先取 80、标注时微调”的模糊口径。若标注时某桶确实不足，必须在冻结前显式修订桶分布、保持总量 90，并记录变更理由；冻结后改动只能升 `frozen-v2`。不得静默少题。

### 4.3 JSONL schema（建议 v2）

保留旧字段，新增字段均为可选，旧脚本可继续读取：

```json
{
  "schema_version": 2,
  "id": "FROZEN-MULTI-001",
  "split": "frozen-v1",
  "bucket": "multi_hop",
  "label_version": "v2",
  "query": "……",
  "conversation_context": [],
  "expected_behavior": "answer_with_conditions",
  "answerable": true,
  "evidence_state": "sufficient",
  "required_slots": [],
  "gold_facts": [
    {"fact_id": "POL-RET-001", "key": "return_window_days", "value": 7,
     "unit": "day", "conditions": ["签收之日起", "商品完好"]}
  ],
  "required_evidence": [
    {"doc": "退货政策.md", "section": "七天无理由退货",
     "quotes": ["商品自签收之日起 7 天内,支持七天无理由退货。"],
     "fact_ids": ["POL-RET-001"]}
  ],
  "required_conditions": ["签收 7 天内", "商品完好"],
  "condition_aliases": {"签收 7 天内": ["七天", "7 天"]},
  "forbidden_claims": ["任何情况都可退", "30 天无理由"],
  "clarifying_slots": [],
  "slot_aliases": {"sku": ["型号", "哪款"]},
  "verification_markers": [],
  "expected_refusal_reason": "",
  "as_of_date": null,
  "requires_tools": [],
  "tool_fixtures": [],
  "source": "synthetic",
  "source_ref": "corpus/facts/policy.yaml#POL-RET-001",
  "annotator": "",
  "reviewer": "",
  "review_status": "draft",
  "notes": ""
}
```

约束：

- `answerable=false` 的题必须有 `expected_behavior=refuse` 和 `expected_refusal_reason`；不得再用“只写 answerable=false、不写期望行为”的旧格式新增题。
- `clarify` 题可以没有 `required_evidence`，但必须有 `clarifying_slots`；检索层单独报告 `n`，不能把它算成检索失败。
- `policy_conflict` 题必须有 `as_of_date`，用于选择生效版本。
- `condition_aliases` / `slot_aliases` 只用于确定性判分，不进入模型上下文；`verification_markers` 用于“需核验”题的流程措辞检查。
- 工具题用 `requires_tools` 列工具名，用 `tool_fixtures` 固化参数与结果；ch11 只记录 fixture，不执行工具，L4 由 ch12 评。
- `verify_then_answer` 必须有流程证据和 `forbidden_claims`，例如禁止“直接判定算质量问题”。
- 数值题必须给单位/容差；金额按分或两位小数；日期/时效按天。
- 多轮题用 `conversation_context` 记录前文，必要时加 `follow_up_turns`；判分按最终轮或逐轮分别报告。

### 4.4 人工标注与分歧处理

判定树（写进标注指南）：

1. 问题是否在业务域内？否 → `refuse`。
2. 知识库是否有足够事实直接回答？是 → `answer`。
3. 事实成立是否依赖条件/资格/时效？是 → `answer_with_conditions`，列出必需条件。
4. 是否缺少用户可补充的槽位？是 → `clarify`，列出必需槽位。
5. 是否必须检测/鉴定/人工核验才能下结论？是 → `verify_then_answer`，只给流程和有限帮助。
6. 以上都不成立 → `refuse`。

流程（本项目分工：Claude Code 实施、Codex 独立验收）：

- 标注者先按指南标注；LLM 只做“第二意见”和缺槽位检查，不作为真值。
- Codex 对冻结集逐题核查证据与标签；业务规则争议提交用户裁决。开发集至少抽审 20%。
- 争议按“证据优先、业务规则优先、用户最终裁决”处理；每条争议记录理由和最终标签。
- 若确有第二位独立标注者，可对冻结集子集做双标并报告一致率（如 Cohen's κ）；κ<0.7 时先修指南，不急着扩题。当前项目只有 Claude Code 标注 + Codex 验收，不得声称“人工双标”或报告 κ。
- 标签变更写 changelog：旧标签、新标签、理由、影响题号、是否重跑旧报告。历史成绩不覆盖。

### 4.5 冻结治理

- 冻结文件提交 git，记录 SHA-256、题量、桶分布、标签版本、审阅人。
- 冻结后禁止按单题调 prompt/阈值；如果失败，只能记录失败分类，修复放到开发集验证，再决定是否升 `frozen-v2`。
- 每次对照报告必须引用同一个 `eval_contract.json`；不同 contract 的结果不可直接比较。
- 允许看冻结集的逐题失败（用于归因），但不允许把失败题的答案写回 prompt 或检索规则后仍声称同一冻结集成绩。

## 5. C04/C05 标签审计

### 5.1 原则

旧标签把“知识库里有相关条款”误当成“可以给出确定答案”。审计要区分：

- **有条件回答**：可以回答，但必须说明会员/商品/时效/地区等条件；
- **确定性结论**：知识库直接给出，无额外条件；
- **需要鉴定/澄清**：缺证据或缺槽位，只能给流程/追问，不能下结论。

不得通过调 prompt 把 C04/C05 硬刷成“答对”。Prompt 只能在 dev 集上迭代，并与冻结集结果分开报告。

### 5.2 C04「这个东西能便宜点不」

- 现状：`answerable=true`，证据为「会员享 95 折、生日礼包、优先客服通道」；蕴含判断器已将其拦下。
- 问题：`这个东西` 没有指代对象；用户是否会员未知；95 折是否适用于该商品/活动未知。把“会员权益存在”当成“该用户可便宜”是过度承诺。
- 已决定标签：`expected_behavior=answer_with_conditions`（按有条件帮助处理）。独立问法缺少商品/会员信息时，回答必须先说明条件或追问，但不得标回确定性答案。
  - `required_slots=["sku","member_status"]`
  - `required_conditions=["会员身份","商品参与活动","最终价格以页面为准"]`
  - `forbidden_claims=["可以便宜", "给你打 95 折", "所有商品 95 折"]`
  - `evidence_state=partial`
- 可接受回答：先问“是哪款商品、是否会员”，可补充“会员通常 95 折，具体以商品/活动为准”，不得承诺。
- 若要变成确定答案，需要业务明确“哪些商品参加、是否叠加、谁有资格”，补进事实库和知识文档，升语料版本后重标。

### 5.3 C05「开胶了算不算质量问题啊」

- 现状：`answerable=true`，证据为「质量问题可凭照片凭证免费退货，退回运费商家承担」；蕴含判断器已将其拦下。
- 问题：知识库没有定义“开胶是否属于质量问题”。用退货条款回答“算不算”，是把流程当判定。
- 已决定标签：`expected_behavior=verify_then_answer`。
  - `required_slots=["order_id","damage_photo"]`
  - `required_conditions=["需售后检测/照片凭证", "是否属质量问题以检测结果为准"]`
  - `forbidden_claims=["算质量问题", "一定可以免费退", "开胶不属于质量问题"]`
  - `evidence_state=partial`
- 可接受回答：说明可提交照片/订单，由售后核验；若认定为质量问题，可按质量退货流程处理；不得直接判定。
- 若要变成确定答案，必须在知识文档中加入明确的“开胶/断裂属于质量问题”规则，并说明适用范围和例外，再重标为 `answer`/`answer_with_conditions`。

### 5.4 其他需要同批审计的高风险题

| 题目 | 风险 | 建议 |
|---|---|---|
| C01 耳机戴两天耳朵疼 | 7 天无理由需“商品完好”，非质量退货运费谁出未说 | 改 `answer_with_conditions`，补运费条件 |
| C02 退款多久到 | 1–3 天仅部分渠道；银行卡最长 7 天 | 补渠道条件，`answer_with_conditions` |
| E01 98 元凑单满 99 | 合并支付/同订单/地址规则 | 补合并订单条件与计算 |
| E03 定制商品过 7 天 | 定制类仅质量问题可退 | `answer_with_conditions`，补质量条件 |
| E04 6 天降噪坏了 | 是否质量问题需核验；运费责任随之变化 | 补质量认定条件 |
| E06 会员买手环 | 95 折是否适用、是否叠加 | 补计算与适用条件 |
| E08 满 99 包邮对偏远 | 包邮后仍补 5 元 | 必须同时说两条 |
| F04 大件取件 | 质量/非质量问题费用责任不同 | 补条件 |

审计范围建议：冻结前对全部 47 条旧正样本做一次 `expected_behavior` 复核；C04/C05 作为阻断项优先处理。

### 5.5 禁止的“刷分”做法

- 不为通过旧标签而放宽证据判定、改 rerank 阈值、在 prompt 中写死答案。
- 不把 C04/C05 从评估集删除来制造提升；可以改标，但必须保留历史版本与说明。
- 不把蕴含判断器的失败简单归因于“模型不听话”；先判断标签是否本来就错。


示例中的模型名 **仅用于展示字段格式，不是选型结论**。回答/改写/裁判模型必须在冻结 manifest 前由用户选定，并核实官方有效名称、价格与可用性；已退役的旧模型名不再作为新评测模型候选。

新语料与新索引会使旧 `config/evidence_calibration.json` 过期：本轮不覆盖生产配置，contract 固定写 `calibration_status="stale"`；候选校准只允许用 dev/regression，不得用 frozen-v1 调阈值。`pricing.verified=false` 时禁止任何付费调用；核实官方价格后才可置 true。

报告中必须原样带出这些字段；缺字段的结果不能进入对照。

### 6.2 冻结项

- 查询改写：冻结缓存，按 split 分开；缓存绑定评估集 SHA + 模型。
- Embedding：固定模型/维度/归一化；建议增加查询 embedding 缓存，按 `(model, text)` 键，减少跨调用波动（历史已观察到同缓存下 dense 结果偶发差 1 题）。
- 索引/语料：记录 build_id、文档哈希、chunk 参数、chunk 数；重建后必须重新跑回归。
- 模型与 prompt：记录模型名、温度、max tokens、prompt 模板哈希；裁判模型与生产回答模型分开记录。
- 阈值：`rerank_score_floor`、证据校准产物、`candidates`、`top_k` 全部进 manifest。

### 6.3 逐题轨迹与失败分类

每题输出一行 JSONL，至少包含：

```text
case_id, split, bucket, expected_behavior, query,
retrieved:[{rank,chunk_id,score}], coverage_rank, group_recall,
gate:{verdict,reason,evidence_state_pred},
answer, citations:[...], deterministic_checks:{...}, judge:{...},
behavior_pred, llm_calls, tokens_in, tokens_out, latency_ms, cost_estimate,
failure_labels:[...], trace_id
```

失败分类枚举（稳定，不随报告改变）：

`retrieval_miss`、`entity_confusion`、`version_conflict_missed`、`evidence_insufficient`、`gate_false_accept`、`gate_false_block`、`answer_wrong_fact`、`answer_missing_condition`、`forbidden_claim`、`citation_unsupported`、`over_refusal`、`under_refusal`、`clarify_missing_slot`、`clarify_over_asking`、`verification_overclaim`、`tool_error`、`timeout`、`cost_over_budget`、`data_error`。

报告按失败分类计数，并给每个分类 3–5 个代表案例；不能只报总错误数。

### 6.4 配对比较与统计

- 同一 `eval_contract` 下比较基线/方案；同题、同语料、同索引、同模型预算。
- 二值结果给逐题 `win/loss/tie` 与 McNemar 精确检验；连续指标给 bootstrap 置信区间。
- 分桶报告；单桶 `n<30` 时只报计数和区间，不宣称统计显著。
- 不允许方案 A 用更大的 top_k、更多检索轮或更贵模型却不计入成本；预算不同必须在报告中拆开。

### 6.5 成本与延迟

- 价格表版本化，记录输入/输出单价与币种；token 用 API usage 口径。
- 费用分为回答模型、裁判模型、embedding、rerank、检索/工具；裁判成本单独列。
- 延迟分 P50/P95，记录是否命中缓存、是否降级、是否重试；离线缓存跑与在线跑分开。
- 报告“质量/成本前沿”，但**不合成单一加权总分**，避免用低成本掩盖误放行。

### 6.6 Milvus Lite 单进程锁与快照边界

现有 Milvus Lite 是单进程文件库，服务运行时并行跑建库/评估会冲突。**“服务运行时直接复制 Milvus Lite 文件即可得到一致快照”尚未验证**；进程仍持有并写入时做文件级复制，可能得到不一致状态，不能当作已成立的能力写入方案。

默认可行方案是**先停写/关闭持有该文件的进程，再复制并校验**，而不是在线直接复制：

- A：评测前停 `uvicorn`（以及建库等写入进程），用进程级文件锁（`flock`）串行化；简单但会中断服务。
- B：停写并确认所有持有 Milvus 文件的进程已关闭后，把文件及其 sibling lock/wal 文件复制为只读快照（如 `data/eval-snapshots/<build_id>.db`）；重开快照后必须完成五项校验，才可在快照上评测：
  1. `build_id` 与构建 manifest 一致；
  2. `pending=0`；
  3. MySQL 与 Milvus 的 chunk id 集合完全相等；
  4. 逐 chunk 的 `text` 与 `category` 都和 `vector_text(category, questions, answer)` 相等（不能只比计数）；
  5. 快照文件 SHA-256 记录进 contract。
  创建前检查 `/proc/*/fd`（或等价手段），发现其他进程仍持有 db 文件即失败。需要短停写窗口、磁盘空间和快照清理策略。
- 若要“不中断服务”的在线快照，或迁移到 Milvus server 版，属于尚未验证/超出 ch11 默认范围的事项，留待用户讨论，本文不承诺。
- 无论哪种，评测脚本启动时都要获取 `data/.eval.lock`，检测到并发运行立即失败并提示；报告中记录 build_id 与快照路径，并注明快照是停写后复制。

### 6.7 复现验收

同一 manifest、同一快照、同一缓存下连续跑两次：

- 确定性指标（检索、证据覆盖、确定性判分）必须完全一致；
- 非确定性指标（LLM 回答/裁判）允许波动，但必须报告两次差异与失败分类是否稳定；
- 若 embedding/rerank 无缓存导致漂移，需在报告中明确标注“未完全复现”，不能把差异当成方案提升。

## 7. 与 ch12 Agentic RAG、ch13 LightRAG 的接口

1. **同一冻结契约**：ch12/ch13 必须读取同一个 `frozen-v1` 与同一 `eval_contract.json`；不得各自造一套“有利于自己”的题。
2. **同题配对**：基线、`仅拆解一次`、`完整受控循环`、纯 LightRAG、hybrid+循环等组合，全部在同一批题、同一语料/索引快照、同一最终答案预算下比较；报告逐题得失，不只报总分。
3. **新题型只进开发集**：ch12 需要多轮补检索、ch13 需要关系题，可以新增到 `dev`；一旦进入 `frozen-v1` 就锁定。若必须新增到冻结集，创建 `frozen-v2` 并重跑所有方法。
4. **方法无法运行的题不能剔除**：某方法不支持多轮或图检索时，该题按失败/拒答计分，并报告覆盖率；不能只评“能跑的题”。
5. **统一失败分类与指标口径**：复用第 2、6 节的枚举和 manifest；ch12/ch13 可以增加诊断指标，但不能改主指标定义。
6. **写操作与工具轨迹**：ch12 的工具调用、幂等键、超时/预算要进逐题轨迹；ch11 冻结集应预留少量多轮/工具题，避免 ch12 上线后才发现没有对照样本。
7. **知识版本一致性**：ch13 的索引更新/删除必须能在同一 `build_id` 语义下回滚；旧版本不得继续回答过期政策。评测报告必须注明索引版本，不能把不同索引的结果混在一张表里。

## 8. 关键方案与取舍

### 方案 A：语料来源

| 选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A1 手写小语料 | 快、可控、易审 | 规模小、语言单一、难构造复杂关系 | 仅适合 P0 |
| A2 结构化事实库 + 受控渲染/手写文档 | 可审计、可构造版本冲突/负例、答案与事实可追溯 | 前期建模和审校成本高 | **推荐** |
| A3 公开电商 FAQ/政策 | 语言真实、量大 | 许可/时效/污染/与事实库不一致 | 只做少量改写参考 |

推荐 A2，理由是 ch11 的核心目标是“可解释的证据链”，不是“更大的文本量”。LLM 只用于问法变体和措辞辅助，不用于生成金标。

### 方案 B：评测框架

| 选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| B1 扩展现有 Python 脚本 | 复用严格 evidence 计量、改写缓存、报告元数据；无新依赖；可控 | 需要自己写回答/裁判/统计层 | **推荐** |
| B2 引入 Ragas/DeepEval 等框架 | 现成指标、生态 | 新依赖、版本漂移、指标口径可能与现有严格判定不一致 | 暂不引入；如引入需先做口径对照 |
| B3 全新自建框架 | 完全定制 | 工作量大、重复造轮子 | 不推荐 |

推荐 B1：在 `eval_metrics.py` 增加纯函数，在现有脚本上增加混合集入口和 manifest；保持“同一套代码跑所有策略”。

### 方案 C：标注与真值

| 选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| C1 单人标注 + LLM 预审 + 用户终审 | 可行、成本低、保留人工责任 | 一致性证据弱 | **推荐（当前单人项目）** |
| C2 双人独立标注 + 裁决 | 一致性强 | 工时高 | 冻结集子集可选用 |
| C3 纯 LLM 标注 | 便宜快 | 不可作为冻结真值 | 不推荐 |

推荐 C1，并明确报告一致率的方法与局限；不要声称“人工双标”如果没有做。

### 方案 D：冻结集可见性

| 选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| D1 标签进 git、靠流程纪律 | 可复现、可审计 | 有过拟合风险 | **推荐默认** |
| D2 用户持有 blind 子集 | 更防过拟合 | 复现和交接复杂 | 可选，作为补充 |

推荐 D1 + 少量 D2；无论哪种，冻结哈希与变更流程必须一致。

### 方案 E：Milvus Lite 评测隔离

| 选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| E1 停服务 + flock | 简单 | 中断服务 | 兜底 |
| E2 停写/关进程后复制快照；重开校验 build_id、pending=0、id 集合、逐 chunk 文本/类别、文件 SHA | 不要求服务持续写入、可复现 | 需要短停写窗口、磁盘开销、快照管理 | **默认可行** |
| E3 服务运行时直接复制 / 在线快照 | 不中断服务 | 一致性未验证，不能承诺 | 待验证，不作为默认方案 |
| E4 迁移 server 版 Milvus | 并发能力强 | 超出 ch11 范围 | 留待用户讨论 |

E2 的关键是复制前停写并关闭持有文件的进程；复制后必须重开快照并按 §6.6 的五项校验（build_id、pending=0、id 集合、逐 chunk 文本/类别、文件 SHA）核验，不能把“复制了文件”或“计数相等”直接等同于“得到了一致快照”。
