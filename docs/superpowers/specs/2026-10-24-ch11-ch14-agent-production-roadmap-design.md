# ch11–ch14 总纲：面向 Agent 开发岗位的 ShopHelper 生产化与 RAG 演进

- 日期：2026-10-24
- 状态：总框架草案，供用户审阅和后续逐章立项；不是逐任务实施计划
- 目标岗位：腾讯 Agent 开发；后端工程与 Agent/RAG 能力并重
- 主场景：沿用电商客服，扩展商品、订单、售后、政策和知识审核数据
- 分工：DeepSeek 按逐章计划实施；Codex 独立验收、复核证据和提出返工意见

## 1. 现状与要解决的问题

ShopHelper 已有 FastAPI/SSE、MySQL、LangGraph、工具注册与审计、MCP、混合检索与重排、证据判断、Langfuse、低置信问题池及知识审核。ch10 已收口；ch04 的严格检索评估和证据闸 v2 已在当前分支提交。已有能力应作为对照基线继续使用。

现有生产边界见 `CLAUDE.md`、`README.md` 与 `docs/handover-to-codex-2026-10-24.md`：Milvus Lite 单进程文件库；图 checkpoint、会话回灌标记和部分反馈快照驻留进程内；多 worker 与同会话并发未作为正式场景验收；后台管理页缺鉴权；物流/售后 MCP 数据为模拟。知识库仅三份源文档、约 59 个块，47 道可答题的 `hybrid_rerank` 严格 R@10 已达 1.000。这些规模和题型不能证明图检索或多轮检索的增益。

本轮目标是形成一条可解释的证据链：**真实业务问题 → Agent 决策与工具/检索轨迹 → 正确且有依据的回答或拒答 → 可恢复的后端执行 → 可重复的质量、延迟和成本对照**。

## 2. 总原则与边界

1. 每章同时交付一项 Agent/RAG 能力和一项支撑它的后端能力，避免只堆框架名称。
2. 保留现有 `hybrid_rerank` 作为冻结对照；新方案先旁路或影子运行，再依据证据决定是否切主路径。不得为了新方案调低严格证据标准。
3. 把“检索到了片段”“证据足以回答”“最终答案正确”分开计量。C04/C05 先重审题目标注和可回答边界，不能靠改 prompt 刷分。
4. 评测集分开发/调参集与冻结测试集；同义改写和同源模板不得跨集合泄漏。每次报告注明语料版本、模型、提示词、缓存、种子、索引配置、运行时间与成本。
5. 所有生产化表述以实测部署形态为准。模拟工具、单机文件库或缺少鉴权的版本称“生产导向原型”，不称已上线生产系统。
6. FinanceBench 保持独立实验线；其英文财报指标不混入中文客服成绩，也不因本路线自动恢复付费评测。
7. 新增技术可以被撤回。每项功能须有开关、降级路径、回滚办法和旧路径的对照结果。

## 3. 章节地图

| 章节 | 主题 | Agent/RAG 主线 | 后端主线 | 进入下一章的证据 |
|---|---|---|---|---|
| **ch11** | 评测与可靠执行基线 | 扩展真实感语料；建立多跳、适用条件、拒答评测；审计 C04/C05 | 会话并发控制、可恢复执行状态、评测与知识版本记录 | 冻结基线、重启/并发验收、数据标注抽审 |
| **ch12** | 受控 Agentic RAG | 证据缺口识别、子问题拆解、有限次补检索、停止/拒答 | 检索步骤持久化、超时与预算、工具写操作幂等 | 与 ch11 同题配对消融，质量收益及延迟/成本代价明确 |
| **ch13** | LightRAG 与知识索引服务 | 关系类语料的图检索试验；与 hybrid、Agentic RAG 正交对照 | 异步入库、索引版本、增量更新/删除、切换与回滚 | 关系题增益、索引/查询成本、更新一致性、来源可追溯 |
| **ch14** | 生产导向交付 | 按评测结果选择检索路由；端到端引用与拒答闭环 | 鉴权、部署、多实例、故障演练、压测、监控告警 | 质量/安全/可靠性/成本总报告与可复现演示 |

章节是决策顺序，不是预先承诺 LightRAG 一定替换线上检索。每章先写独立 spec 和实施计划，经用户确认后再交 DeepSeek。

## 4. ch11：评测与可靠执行基线

### 要解决的问题

当前 47 正题 + 13 负题可用于回归，但范围和样本量不足以比较新架构。当前基线还缺完整的多进程、重启和同会话并发证据。先让后续每一步有可信的参照。

### 范围

- 扩充电商语料：增加商品型号与兼容/替代关系、优惠适用范围、订单状态、退换修政策版本、物流异常和需要跨文档组合的情况。数据为演示数据时明确标注；源文档、结构化业务事实与问答标签分开维护。
- 新评测覆盖：单文档直答、跨文档/跨工具多步、含多约束规则、实体错配、过期政策冲突、同域硬负例、无答案和应澄清的问题。每条有证据来源、期望行为、人工审核记录。
- 对 C04/C05 重标：C04 允许有条件说明会员折扣但不得承诺任意商品/用户可享；C05 在没有“开胶”的正式判定规则时应回答需核验，不能直接认定质量问题。评测要区分“可给有限帮助”和“可给确定结论”。
- 评测脚本报告检索层、证据层、答案层与过程层，保留逐题结果和失败分类；冻结查询改写、embedding、索引/语料版本，避免跨轮噪声被当成提升。
- 后端补同会话并发策略和持久执行状态。明确崩溃点、重放边界、SSE 断开行为和幂等键；在重启、并发和数据库故障演练中核对 MySQL 真源。

### 验收门槛

1. 冻结测试集在方案开发前锁定，正负例数量、来源和人工抽审结果公开；旧 60 题保留作回归，修订标签另记版本，不覆盖历史成绩。
2. 每次评估可凭同一配置/缓存复现；报告含逐题、分类型、总体指标与置信区间或配对差异，不只报一个总分。
3. 同一会话并发及进程重启后不出现重复写工具、会话串线或已确认订单动作丢失；故障案例留有可查轨迹。

## 5. ch12：受控 Agentic RAG 与可恢复执行

### 要解决的问题

现有商品咨询主要是一次检索、一次证据判断。跨块、多约束问题缺证据时，直接拒答可能错过可通过补检索找到的答案。Agent 应能说明缺口并按预算补查。

### 预期流程

`首次检索 → 判断已覆盖的事实与缺口 → 选择澄清/子问题/补检索 → 合并去重并检查冲突 → 证据充分则回答，否则拒答或转人工`。

- 只有经 ch11 题型和错误分析证明值得补查的问题进入循环。明确最大检索轮数、token/时间预算和终止理由；同一查询不得无意义重复。
- 检索决策、子问题、使用的工具、证据 ID、冲突处理和停止原因进入 trace 与评测报告。答案的每个重要结论可回指证据；写工具仍受现有确认与权限闸约束。
- 节点执行可恢复；超时、模型故障、检索故障时按已知证据谨慎收敛。外部写操作使用幂等键，不因图重放重复建单或修改业务状态。

### 对照与验收

同题比较：`ch11 基线`、`仅拆解一次`、`完整受控循环`。固定语料、模型与最终答案预算，报告证据覆盖、答案正确/引用支持率、错误放行、合理拒答、平均/P95 延迟、每题调用次数和成本。重点给出 `E_multi` 与新增多步题的逐题得失。没有净收益时保留基线路由，不用“Agentic”名称代替结果。

## 6. ch13：LightRAG 对照与知识索引服务

### 要解决的问题

商品、型号、配件、订单和政策适用条件形成实体关系；平面 chunk 检索可能需要多次跳转。LightRAG 的图与双层检索是否值得生产接入，要在这类语料上证明。

### 范围

- 在独立索引中试验 LightRAG，保留原文片段与来源 ID。图抽取可能错误；图上的关系只能作为检索线索，最终事实须回原文或可信结构化数据核验。
- 同步比较四组：现有 hybrid+rerank、LightRAG、hybrid+受控循环、LightRAG+受控循环。控制 embedding、LLM、重排、候选/上下文预算，单独计入建索引与增量更新费用。
- 建知识入库任务与版本：提交、解析、抽取、嵌入、图更新、可查询、失败/回滚状态可追踪；删除或更新政策后旧版本不得继续给出过期答案。
- LightRAG 默认文件存储只作试验；若进入服务路径，选择可持久化且可运维的存储方案，并验证备份、恢复、并发与版本切换。不得把本地试验结果直接称生产可用。

### 进入主链路的条件

关系类题在冻结集上有稳定、可解释的配对收益；硬负例、实体错配与政策过期题没有不可接受的误答增加；查询延迟与总成本处在事先约定的预算内；更新、删除、恢复与回滚通过故障演练。未满足则保留为对照实验，不能强行切主路径。

## 7. ch14：生产导向交付

- 对管理、审核、知识写入及工具写操作加入身份与权限控制；记录谁批准了什么。处理敏感数据脱敏、日志保留与最小权限。
- 在多实例部署中验证会话状态、任务队列和索引访问；模拟 MySQL、向量库、模型服务、MCP 的超时/失败，验证有界重试、熔断、降级与恢复。
- 用固定负载分层压测普通问答、多步检索与写工具确认流程；报告吞吐、成功率、P50/P95/P99、首 token 时间、token/请求、成本/请求，说明硬件和并发设置。
- Langfuse/本地指标贯通请求、Agent 步骤、检索、工具、知识版本与最终答案；看板可定位质量退化、超预算、误拒答和误放行。
- 按 ch11–ch13 的对照结果决定生产路由，配置开关与回滚演练；形成部署手册、验收脚本、故障复盘和可复现演示。模拟数据或单机限制在报告中清楚标示。

## 8. 统一验收与协作协议

### DeepSeek 每章交付

1. 该章独立 spec、实施计划和决策记录；说明改动边界、数据/接口契约、回滚方案。
2. 代码与迁移、测试、演示/验收脚本；保留基线和逐题评测产物。不要把 FinanceBench 的未提交实验内容混进章节提交。
3. `dev-notes/chNN.md` 记录关键决策、失败与返工、实测结果；`README.md` 给出最短复现步骤。报告中区分模拟、离线评测与真实部署。
4. 交付时提供精确 commit/分支、修改清单、运行命令与完整输出摘要，以及已知风险；不以“测试通过”代替实际验收。

### Codex 每章验收

1. 对照该章 spec 逐项核实代码、数据、迁移和交互行为；独立复跑关键测试与端到端案例，不直接采用实施者自报数字。
2. 检查评测是否同题、同语料、同模型预算，是否有调参集泄漏、选择性报告或旧版本索引；抽审正负样本和引用来源。
3. 检查并发、幂等、重启、超时、回滚及数据权限；记录可复现的问题并要求返工，复验通过后才建议收章。
4. 给用户一页验收结论：已通过、未通过、数字及其分母、复现命令、成本与剩余风险。章节是否合并、推送或对外展示由用户决定。

### 跨章硬门槛

- 每章必须保留上章基线与版本，不以覆盖旧报告的方式制造提升；关键指标注明分母和运行条件。
- 错误放行、无证据断言、重复业务写入和越权操作为阻断项；召回或回答率提高不能抵消这些问题。
- 质量收益须与延迟、调用数、索引成本一起报告；复杂度增加而没有可重复收益的方案不进入主路径。

## 9. 立项顺序与未定参数

先立 ch11；其冻结数据集和可靠性基线是后续实验的共同地基。ch12 的补检索范围、ch13 的存储选型与 ch14 的负载目标，应在各章启动时根据 ch11 实测和可用资源定稿。本总纲不预设提升百分比，也不预设 LightRAG 必须上线。

用户审阅本总纲后，逐章写独立设计与执行任务。DeepSeek 负责实施，Codex 负责验收；在没有该章实测证据前，简历和项目介绍只写已完成能力。
