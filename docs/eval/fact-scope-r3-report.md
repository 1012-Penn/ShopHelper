## 结论

订单事实冲突的主因是命名空间缺失,不是订单字段本身。修复后,结构化查询把裸数字固定为
`legacy_demo`,完整 `ORD-*` 固定为 `corpus`,并返回可追溯来源、数据版本、as-of 和缺失字段。
held-out 上主体匹配从 5/20 提升到 18/20,最终任务成功从 5/20 提升到 17/20,实体串用从
7/20 降到 0/20。

可解释 scope 过滤在 held-out 上把 R@K 从 8/9 提到 9/9、剔除误伤为 0,但两臂任务成功均为
17/20。它带来更短上下文和更低 P95,没有证明回答成功净增益,因此保持可选,不把 R@K 提升写成
回答能力提升。

## 事实冲突修复

同一个末四位现在得到两个明确主体:

| 输入 | 主体 | 当前事实 |
|---|---|---|
| `1001` | `legacy_demo:1001` | 无线耳机,299 元,已签收 |
| `ORD-1001` | `corpus:ORD-1001` | 248 元,未支付 |

`corpus` 视图通过 `app/business_facts/manifests/corpus-orders-v1.yaml` 映射不可变 factbook。
结构化事实负责状态、金额、会员、地区、支付渠道;签收/下单时间只在有明确来源的 overlay 中登记。
商品字段在当前 factbook 缺失时返回 `missing_fields`,不从另一单或相似商品补齐。

旧裸数字调用、`ORDER_CATALOG` 三单、未知上下文订单话术均保留。`list_orders()` 默认仍为
legacy 三单,显式 `namespace="corpus"`/`"all"` 才读取新视图。

## Scope 机制

`EvidenceScope` 携带 canonical subject、政策版本和参考日期。过滤只剔除:

- 文档显式引用另一个 `ORD-*`;
- 标题显式标注另一个政策版本;
- 标题版本在 factbook 中有明确生效区间,而参考日期落在区间外。

泛化政策和 scope 未知项保留,不会因为缺少订单号全部丢弃。过滤为空时返回
`作用域过滤后无适用证据`,不触发无过滤回退。输出保留 `scope_status`、被排除 chunk 及原因、
未知 chunk 与匹配 chunk;held-out 9 个有合法金标的 scope 题没有误过滤。

## 失败与局限

- `FSR3-HLD-011`: 订单 `ORD-1001` 没有签收时间。三臂都说明无法确认并在正确条件下补答,但
  输出 `action=answer` 而 gold 为 `clarify`,故仍计失败。这是动作标签与“回答并澄清”交界处失败。
- `FSR3-HLD-017/018`: identity/scope 把假设日期中的年份 `2026` 当成裸订单号。held-out 后已
  用回归测试修复日期年份误抓,但没有重跑 held-out;因此这两题的主体失败原样保留在分母。
- `FSR3-HLD-017` scope 回答末尾的条件句正确写了“若实际为 2026-06-01 之后则适用 v2”,
  仍被简单禁止短语评分命中。该条件是合理说明,但未事后改分。
- 真实模型对照走确定性 SQLite + 测试 embedding/reranker,不是 Milvus/BGE 端到端性能;
  同时 harness 直接提供工具/证据上下文,没有评测完整 Agent 的自主工具选择轨迹。
- 样本只有 28 题,held-out 分组数量小,不能推广为线上成功率。
