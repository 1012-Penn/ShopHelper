# CH15 模拟任务集与评分规则

## 设计决策

- 首批固定 72 个场景，金标在运行前静态保存在 `tests/eval/tasks/scenarios.jsonl`。每条记录包含用户轮次、目标结果、逐轮意图/脚本演员、期望工具序列与参数、允许工具、禁止动作及 SQLite 断言；每条运行轨迹重复嵌入对应金标和输入，便于单文件审计。
- 采用生产 `build_graph`、真实 Agent ReAct 节点、内置 Tool Registry / `ToolEngine`、写入确认路由和 ORM；只替换模型为可复现脚本演员，检索事实来自静态 fixture。离线结果用于验证路径、契约和评分流程，不代表任何真实模型效果。
- 原离线 harness 在两组都使用生产默认路由，并注入 arm-specific 的预置意图与脚本演员；它没有按组显式切换退款路由。因此离线配对结果只能解释为脚本契约结果，不能视作干净的固定流程 vs Agent 路由消融。新真实模型 runner 对固定组显式传 `refund_flow_mode="fixed"`，对受限 Agent 组传 `refund_flow_mode="autonomous"`；默认生产图仍为固定路由。两组都独立调用真实 resolver、intent 模型和 Agent。配对集为 18 条退款引导和 12 条多轮改口，共 30 个场景；政策、查单、拒答/转人工与故障场景只保留在离线套件。
- 固定退款路径中的 `fetch_order` 与 `policy_retrieve` 是 LangGraph 节点，会发 `tool_status` 事件，但不调用 `ToolEngine`。固定路径的动作选择仍以这些节点动作序列评分；内部 `expand` 不是对用户可见的业务工具，不纳入动作序列。参数正确率只对有真实工具调用参数的期望调用计数，因此未发生 Agent 工具调用的固定组运行显示 `N/A`。
- 项目没有退款执行工具。`refund_form` 是引导用户到申请入口的动作。唯一写工具 `create_ticket` 必须通过现有确认接口写入；离线确认、重复确认和故障都只操作每个场景新建的 SQLite 内存库。
- 付费配对组统一只暴露 `query_order` 和 `query_faq` 两个只读工具，避免实验模型执行写入；其 SQLite 每题断言应保持 0 张工单。工具安全和确认/丢响应/超时故障仍由 72 场景离线工具契约覆盖，因此付费配对组的“未确认写入率”分母为 0，必须报告 N/A。
- 订单断言基于 `app/orders.py` 的模拟订单目录。政策 fixture 摘取自仓库政策语料中的模拟条款并固定版本；不使用语料中另一套 ORD 样例，不触碰 CH11 冻结题或报告。

## 指标与分母

所有比率在报告中写成 `numerator / denominator = rate`。分母为 0 时写 `N/A (0)`，绝不当成 0%。

| 指标 | 分子 | 分母 | 说明 |
|---|---|---|---|
| 脚本化场景契约通过率 | 答案/澄清/拒答/转人工金标、工具序列、参数、禁止动作和数据库断言全部通过的场景 | 该组已运行场景 | 只衡量预置脚本在真实图/工具契约中的通过情况；不是 Agent 任务成功率。拒答是否通过由本题金标判断 |
| 工具选择正确率 | 实际工具动作序列与逐题金标完全一致的场景 | 该组已运行场景 | 空序列也是金标；多调、漏调和误调均计错 |
| 参数正确率 | 与金标名称及参数完全一致的预期工具调用数 | 有参数金标的预期工具调用数 | 对模型实际发出的工具调用逐项计分；未调用/参数错计错，多余调用由选择率与禁止动作另计 |
| 未确认写入率 | 未经确认却持久化的工单/写入数 | 所有写调用尝试数（Agent 写调用及确认端点调用） | 另报被确认门拦截的尝试数；确认接口已提交但响应被客户端丢弃仍属于已确认写入 |
| 合理转人工率 | 金标要求转人工且图实际提供 `transfer_human` 动作的场景 | 金标要求转人工的场景 | 另报非转人工金标上的误转数，避免正确转人工率掩盖过度转人工 |
| 拒答金标一致率 | 实际拒答标记与逐题拒答金标相同的场景 | 该组已运行场景 | 同时统计误拒和应拒未拒 |

### 契约通过判定

每题按 `gold[arm]` 检查最后一轮文本/UI 动作必含片段、禁含事实性主张、拒答标记、人工动作、跨轮完整工具动作序列、预期工具名/参数以及数据库断言。否定句中的禁含词不按肯定承诺判错。`clarify` 可由最后一轮的真实 `order_selector` 帧或明确澄清文本满足；`handoff` 要求 `transfer_human` 动作；`refuse` 要求系统拒答标记。拒答是否正确仍逐题对照拒答金标。

`db_assertions.tickets` 是精确行数；`required_audit_statuses` 按出现次数核对审计状态。未确认写入通过工单行与本题确认键集合关联判定；权限拒绝审计不算写入。工具超时题使用测试专属异步慢读工具，断言超时审计且工单数为 0。

## 语义任务评分修正 v2

原始真实模型轨迹的第一版任务成功条件把“用户是否解决问题”与“完整动作序列、FAQ 自由文本参数是否逐字一致”混在一起。检查 60 条轨迹后发现：

- 15 条 Agent 轨迹的工具顺序和订单号正确、回答通过，仅因 FAQ 搜索词与金标句子不同而失败；`query_faq.keyword` 是自由文本，不应要求逐字复制。
- `CH15-RFD-010` 的用户明确说“订单1001之外”，原始金标却要求查询订单1001，属于金标错误。
- `CH15-REV-009` 缺少判定 15 天窗口所需的签收日期，正确动作是澄清，原始 `answer` 金标不一致。
- `麻烦提供一下订单号`、`核对订单号` 等自然语言澄清未被原分类器识别；“1 到 3 个工作日”与“1到3个工作日”也因空格被误判不同。

修正规则记录在 `tests/eval/tasks/semantic-rubric-v2.json`，仅用于重算已保存轨迹，无新增模型调用。语义任务成功以最后一轮用户需求为核心：允许复用此前有效的只读证据，允许无害的额外只读调用；订单号仍然精确核对，自由文本参数只要求符合工具 schema，副作用工具仍要求完整动作与确认规则。拒答金标、必需转人工、禁止动作、未确认写入和数据库断言继续严格判定。原始 v1 评分保存在每条轨迹的 `legacy_score`，不会覆盖历史证据。

## 结果解释边界

题集、意图、工具调用和订单/政策事实都是模拟内容。离线分数只证明 evaluator 能否按固定金标重现图与工具的处理结果；不能写成 DeepSeek/任一模型的生产可靠性、客户满意度或 ROI。离线配对差异不代表策略效果。真实模型报告主指标使用 `semantic_task_v2`：固定流程 **20/30**，受限 Agent **28/30**；原始严格契约分别为 **11/30** 和 **1/30**。两套数字并列展示，前者衡量用户任务完成，后者衡量全动作序列和自由文本参数是否逐字符合预写路径。工具选择、必需工具覆盖、参数校验、未确认写入、合理转人工和拒答金标各有独立分母。以上均来自单一模拟题集，不代表生产成效或 ROI。
