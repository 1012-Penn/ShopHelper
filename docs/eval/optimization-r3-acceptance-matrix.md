## 验收闸门

1. 源分支提交基于 `59e233f`，工作区干净；只读源 worktree，不 reset 或覆盖。
2. 逐题轨迹可复算报告中的分子、分母、配对得失、调用、token、费用和 P95。
3. 新 held-out 在运行前冻结题集、配置和评分版本；一次运行后保留失败，事后修改另开版本并全组重评。
4. 实际模型输入不含 gold、expected behavior、评分规则或不允许的业务金标。
5. `uncertain` 不计为 supported；技术失败、评分失败和模型能力失败分开记录。
6. 动作路径必须检查结构化 artifact 和写入 sink；“写尝试为 0”不能单独证明安全成功。
7. 同主体、同尾号不同命名空间、同型号不同订单、政策版本边界、确认同键一单、取消、一次修复上限、
   引用归属和无证据澄清进入组合回归。
8. 应用工厂必须证明新接线的真实入口；只有 CLI 或测试构造器通过不算生产接线。
9. 已有 `/api/chat` 的 run、SSE、租约和恢复语义，以及 `/api/multi-agent/chat` 的确认响应兼容不得倒退。
10. 组合 smoke 使用独立账本、调用前预留、至多两次有界重试、新增费用上限 `$2`；
    它不是新 held-out，也不继承源实验余额。
11. 定向测试和既有 fault acceptance 先通过；集成完成后全量 pytest 一次，只有新失败才补跑。
12. `git diff --check`、凭据扫描和本阶段改动范围的 lint 必须记录实际结果。
    第二轮遗留的“Ruff 全仓通过”声明不可复现（全仓 483 项、相关文件 13 项），本轮必须更正，
    不做全仓格式重构，也不把宽泛检查写成全绿。

## 组合语义

| 现有契约 | 集成门槛 |
|---|---|
| legacy `1001` 订单工具 | 原有三单 fixture 和裸数字调用继续可用 |
| corpus `ORD-1001` | 完整 ID 保留前缀；不能按数字部分映射到 legacy 订单 |
| 结构化订单事实 | 当前状态、金额、签收日期以显式来源为准；知识库不得用另一订单替代 |
| 多 Agent ticket preview | preview artifact、awaiting confirmation、confirmed/cancelled/failed 状态可区分 |
| 客户端确认 | 模型只能请求预览；确认由客户端明确动作触发，同 confirm key 最多一次写入 |
| 自由文本答案 | 原路径保留；答案计划路径可显式选择并回滚 |
| 持久 run 与 SSE | 新增节点或可选服务不得破坏已有恢复、usage 和事件顺序 |

## 合并顺序

1. 独立审查并临时集成事实真源的纯适配层和检索 scope，先跑其定向测试。
2. 集成动作契约模块与 multi-agent 运行时补丁，复核确认、取消和写 sink。
3. 集成答案计划纯模块，再由最终验收会话补最小 graph/config/factory 接线。
4. 解决共享文件冲突后，运行三方向组合回归和一次小规模真实应用 dev smoke。
5. 更新第二轮证据中不可复现的 lint 声明，生成第三轮最终验收、简历证据和开发笔记。
6. 本地提交并安全快进 `main`；不 push，不归档或删除任何工作区。
