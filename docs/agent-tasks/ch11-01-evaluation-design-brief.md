## 设计稿要求

写入 `docs/superpowers/specs/2026-10-24-ch11-evaluation-baseline-design.md`：

1. 评测要回答哪些具体问题；明确“检索命中、证据足够、回答正确、合理拒答、过程成本”各自的标签、分母和指标。
2. 语料扩展策略：保持电商客服业务闭环，增加真实感的商品关系、订单状态、政策适用条件、版本冲突与跨文档证据。给出可审计的数据来源、规模分阶段目标和防止答案泄漏的办法。
3. 数据集设计：开发集、冻结测试集、回归集；单跳、多跳、多约束、实体错配、硬负例、应澄清题等题型；人工标注和分歧处理。
4. C04/C05 标签审计：区分有条件回答、确定性结论、需要鉴定/澄清，不用调整 prompt 硬刷指标。
5. 运行与复现：固定查询改写、embedding、语料/索引、模型与 prompt 版本；逐题轨迹、失败分类、配对比较、成本/延迟；需要考虑现有 Milvus Lite 单进程锁。
6. 与后续 ch12 Agentic RAG、ch13 LightRAG 的接口：两者要复用同一冻结评测契约，不能各造一套有利于自己的题。
7. 至少列出 2–3 个关键方案及取舍。对影响架构、外部依赖、数据来源或费用的选择，写出推荐和待用户决定的问题，不要代替用户拍板。
8. 给出阶段验收标准、风险、回滚方式和哪些数字可以/不可以写进简历。
